Identity Security Sentinel Entra ID
Tracing an impossible-travel alert to a compromised credential
A risky sign-in alert flagged a user account logging in from two geographically distant locations within minutes. Investigation across Entra ID sign-in logs and Sentinel confirmed credential compromise before any lateral movement occurred.

What the alert showed

Sign-in 1 — Successful, Kochi, India
Normal sign-in pattern, matching the user's known device and typical working hours.
Sign-in 2 — Successful, foreign IP, 9 minutes later
A second successful sign-in from an unfamiliar ASN and country, with no physical travel possible in that window — Entra ID's impossible travel detection fired correctly.

Investigation timeline

  • Alert triggered
    Risky sign-in flagged in Entra ID, surfaced in Sentinel
    Entra ID's risk detection engine flagged the second sign-in as "atypical travel." The alert was correlated in Sentinel against the user's authentication history.
  • Investigated
    Sign-in logs reviewed for device, location, and client app
    The second sign-in used a different OS and browser fingerprint than the user's registered devices, with no corresponding Conditional Access device-compliance match — ruling out a VPN or travel false positive.
  • Validated
    User confirmed they had not signed in from that location
    Direct contact with the user ruled out legitimate remote work or travel, confirming the second sign-in was unauthorized.
  • Root cause
    Credential compromise, MFA not enforced on the account
    The account had not yet been brought into the org's Conditional Access / MFA enforcement rollout, leaving a single password as the only control.
  • Resolution
    Session revoked, password reset, MFA enforced
    Active sessions and refresh tokens were revoked, the password was force-reset, and the account was added to the Conditional Access policy requiring MFA — closing the gap that allowed single-factor compromise.
Why password reset alone wasn't enough
Without revoking active sessions, an attacker holding a valid token can stay authenticated even after a password change. Token revocation was the first containment step, before remediation.
Why this wasn't a false positive
Device fingerprint mismatch + user denial + geographically implausible timing together ruled out VPN/proxy explanations, which is the most common false-positive cause for impossible-travel alerts.
SigninLogs
| where TimeGenerated > ago(7d)
| where ResultType == 0
| summarize Countries = make_set(Location), Logins = count() by UserPrincipalName, bin(TimeGenerated, 1h)
| where array_length(Countries) > 1

Key learnings

✓
Risk-based sign-in alerts are only as useful as the speed of the human triage behind them — session revocation has to happen before password reset, not after.
✓
Accounts excluded from Conditional Access rollouts are the weakest link — partial MFA enforcement leaves predictable gaps attackers can probe for.
→
Built a recurring KQL query to flag any account authenticating from more than one country within an hour, to catch similar cases earlier.
Vulnerability Management Nessus / Burp Suite Web Application Security
From scan noise to validated risk: prioritizing a critical SQLi finding
A routine vulnerability scan returned 40+ findings across a client's web application stack. Manual validation separated real exploitable risk from scanner noise, surfacing one critical SQL injection that needed immediate remediation.

Two categories of risk

Category A — Confirmed exploitable, needs immediate fix
A login form parameter was vulnerable to SQL injection, confirmed manually in Burp Suite by injecting a boolean-based payload and observing a behavioral difference in the response.
Category B — Scanner noise, not exploitable in context
Several "high" severity flags from the automated scan were outdated TLS cipher warnings on internal-only endpoints with no external exposure — downgraded after validating network segmentation.

Investigation timeline

  • Scanned
    Nessus scan across endpoints and web applications flags 40+ findings
    Automated scan results came back with a mix of critical, high, and medium severity findings, several without clear business context.
  • Triaged
    Findings sorted by exploitability and exposure, not just CVSS score
    Internal-only systems and findings requiring local access were deprioritized in favor of internet-facing application vulnerabilities.
  • Validated
    SQLi confirmed manually in Burp Suite, not just scanner output
    A crafted payload against the login parameter produced a measurable timing/response difference, confirming the injection point was real and exploitable — not a scanner false positive.
  • Escalated
    Finding reported to the application team with reproduction steps
    Documented the exact request, payload, and observed behavior so the dev team could reproduce and patch without needing scanner re-runs.
  • Resolution
    Parameterized queries deployed, fix re-validated
    After the application team deployed parameterized queries, the same payload was re-tested in Burp Suite and confirmed the injection point was closed.
Why manual validation mattered
Scanner severity ratings don't account for network exposure or business context. Without manual triage, the real SQLi risk could have been buried under 39 lower-priority alerts.
Why this combo of tools
Nessus for breadth across the endpoint fleet, Burp Suite for depth on web application logic — automated scanning catches coverage gaps, manual testing catches exploitability.

Key learnings

✓
CVSS score alone is a starting point, not a prioritization strategy — exposure and exploitability decide what gets fixed first.
✓
A reproducible payload and clear write-up gets vulnerabilities patched faster than a raw scanner export ever does.
→
Maintained a running patch compliance tracker across endpoints to keep remediation SLAs visible to both the security and application teams.
Email Security Defender for Office 365 Threat Explorer
Catching a credential-harvesting campaign before user impact
A user-reported phishing email turned into a wider investigation revealing a small credential-harvesting campaign targeting multiple users across a client tenant, traced and contained using Defender for Office 365 and Threat Explorer.

What the report looked like

Surface signal — One user-reported phishing email
A single employee flagged a "password expiry" email mimicking the organization's IT helpdesk, with a link to a credential entry page.
Underlying signal — Same campaign sent to 5 other users
Threat Explorer search on sender characteristics and subject line revealed the same message had landed in five other inboxes, none of which had been reported yet.

Investigation timeline

  • Reported
    User flags suspicious "password expiry" email
    Email reviewed in Defender for Office 365: sender domain didn't match the organization's actual domain, and the link redirected through a URL shortener.
  • Expanded search
    Threat Explorer query run across the tenant for matching sender/subject
    Searched on sender IP, spoofed domain, and subject line pattern to identify every mailbox that had received the same or a near-identical message.
  • Checked for impact
    Sign-in logs reviewed for the 5 additional recipients
    Cross-referenced Entra ID sign-in activity for each recipient around the time the email landed — no anomalous authentication found, indicating no one had clicked through.
  • Contained
    Emails purged tenant-wide, sender domain blocked
    Used Defender's purge action to remove the email from all 6 mailboxes and added the spoofed sending domain to the block list.
  • Resolution
    Targeted awareness note sent to affected users
    A short heads-up was sent to the 6 recipients describing the specific email so they'd recognize it, plus a reminder on reporting suspicious mail before clicking.
Why one report wasn't the whole picture
Phishing campaigns rarely target a single user. Treating each report as an isolated case misses the wider blast radius — Threat Explorer's tenant-wide search closed that gap.
Why sign-in logs, not just email logs
Confirming an email was delivered doesn't confirm it was acted on. Checking Entra ID sign-in activity for the recipients was the only way to verify no credentials were actually entered.

Key learnings

✓
Every phishing report is a starting point for a tenant-wide search, not a closed ticket once the one email is handled.
✓
Sender domain and header analysis catches spoofing faster than relying on content alone — attackers reuse infrastructure across campaigns.
→
Recommended adding the spoofed domain pattern to a standing detection rule to catch repeat attempts automatically.
Penetration Testing Kali Linux · Metasploit Vulnerability Assessment
Validating a known RCE vulnerability end-to-end — vsftpd 2.3.4 backdoor
A controlled lab exercise using Kali Linux and Metasploitable 2 in VirtualBox, demonstrating the full vulnerability assessment lifecycle: network discovery, service enumeration, exploitation validation, impact assessment, and remediation — the same methodology applied in real-world security operations.
⚠️ Performed entirely within an isolated VirtualBox lab environment (Kali Linux → Metasploitable 2). No real systems were involved.

What the scan revealed

Nmap discovery — vsftpd 2.3.4 exposed on port 21
Service version scan identified vsftpd 2.3.4 running on the target — a version known to contain a deliberate backdoor introduced via a compromised source package in 2011, allowing unauthenticated remote command execution.
Exploitation confirmed — root shell obtained via backdoor trigger
The Metasploit module for vsftpd 2.3.4 triggered the backdoor by sending a specific username pattern, opening a shell on port 6200 with root privileges — full system compromise with no credentials required.

Assessment timeline

  • Discover
    Nmap host and port scan identifies live target and open services
    A full port scan revealed multiple open services including FTP (21), SSH (22), Telnet (23), HTTP (80), and others — a wide attack surface typical of intentionally vulnerable lab targets.
  • Enumerate
    Service version scan flags vsftpd 2.3.4 on port 21
    Running nmap -sV returned the exact service version, which was immediately cross-referenced against known CVEs — vsftpd 2.3.4 has a well-documented backdoor (CVE-2011-2523).
  • Identify
    CVE-2011-2523 confirmed — backdoor inserted via compromised source
    The vulnerability stems from a malicious modification to the vsftpd 2.3.4 source code: a backdoor that listens on port 6200 when a username ending in a specific character sequence is sent during the FTP handshake.
  • Validate
    Metasploit exploit confirms root-level RCE
    Used the exploit/unix/ftp/vsftpd_234_backdoor Metasploit module to trigger the backdoor and obtain an interactive root shell — confirming the vulnerability is fully exploitable with no authentication.
  • Assess impact
    Root access = complete system compromise
    With root privileges, an attacker could read/modify any file, create persistent backdoors, pivot to other network hosts, exfiltrate data, or wipe the system — total loss of confidentiality, integrity, and availability.
  • Remediate
    Patch, isolate, monitor — defensive translation of the finding
    Translated the technical finding into defensive actions applicable to real environments: upgrade or replace the service, remove legacy FTP exposure, maintain accurate asset inventories, and continuously monitor for exposed attack surfaces.
# Network discovery
nmap -sV -p- <target-ip>

# Metasploit exploitation
use exploit/unix/ftp/vsftpd_234_backdoor
set RHOSTS <target-ip>
run

# Result: root shell on port 6200
Why version scanning matters
Service version enumeration is what turns "port 21 is open" into "this specific version has a known backdoor." Asset inventories without version tracking miss this entirely — which is why version-aware scanning is a non-negotiable part of vulnerability management.
Offensive understanding → defensive value
Validating exploitability changes how findings get prioritized. A scanner flagging vsftpd 2.3.4 is a data point — understanding that it yields unauthenticated root in seconds is what makes it a P1 remediation, not a scheduled patch.

Key learnings

✓
The full assessment lifecycle — Discover → Enumerate → Identify → Validate → Assess Impact → Remediate — applies equally to lab environments and production security operations.
✓
Legacy services left running are not just a compliance gap — they are exploitable paths to root. Service exposure should be audited continuously, not just at deployment.
→
Understanding attacks from the offensive side makes defensive recommendations sharper — patch urgency, network segmentation, and monitoring rules all become more precisely scoped.
